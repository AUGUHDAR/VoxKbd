## 1. 项目概述

### 1.1 背景与问题（Background）

在大型 Minecraft（下简称 MC）整合包（Modpack）中，玩家经常安装数十至上百个模组。每个模组都会向原版（Vanilla）按键系统注册自己的按键绑定（Keybinding），导致：

- 原版按键数量有限，整合包内按键冲突严重、不够分配；
- 玩家难以在不覆盖原版操作的前提下为模组功能分配按键；
- 现有方案往往绑定死按键、与具体版本耦合，难以跨版本复用。

**Vox Kbd** 的核心目标：通过引入"虚拟键盘（Virtual Keyboard）"这一概念，在不改动原版按键体系的前提下，为整合包提供**可无限扩展的按键层**，从根本上解决"按键不够用"的问题。

### 1.2 目标（Goals）

- 提供多套虚拟键盘，玩家可在它们之间切换，从而把"物理按键 × 虚拟键盘数量"作为可用按键空间。
- 提供"锁（Lock）"机制，保证特定按键（默认含全部原版按键）在任何虚拟键盘下都稳定映射到默认键盘。
- 通过**独立外部 Java 进程**承载虚拟键盘逻辑，以实现**全版本兼容**，并在进程异常时具备自愈与降级能力。
- 提供完整、可本地化、可配置的总控 UI 与配置界面，且**所有文案与 UI 元素禁止硬编码**。
- **兼容全平台**：Windows / Linux / macOS / Android（Android 通过 FCL、ZL2 等 JVM 启动器运行），见 4.0。

### 1.3 非目标（Non-goals）

- 不替代原版按键系统的注册机制，只做"叠加层"。
- 不管理其他模组内部的按键逻辑（仅以原版按键为准进行锁保护，见 [3.4](#34-按键锁-lock)）。
- 不在第一次实现中追求对全部加载器（Forge / NeoForge / Fabric）的完整支持（见待确认项）。

### 1.4 已确认的关键决策（Decided）

以下为评审已确认、将直接纳入实现的决策（2026-08-20）：

| # | 决策点 | 结论 |
|---|--------|------|
| D1 | 目标加载器与版本 | 首版做 **Fabric**，目标 MC 版本为 **Java 版 26.2「混沌立方」**（2026-06-16 发布，确为有效版本，非笔误）；后续扩展至全加载器。核心逻辑与加载器解耦。 |
| D2 | 虚拟键盘模型 | **新增系统级合成键（Synthetic System-Level Keys）**：模组在输入层**新增**按键（vanilla 仅物理 QWERTY 键盘，无此类键）。每套虚拟键盘是若干合成键的集合。**内部键名固定**为 `VOXKBD_<虚拟键盘序号>_<物理键标识>`（如 `VOXKBD_1_W`、`VOXKBD_2_A`）；`VOXKBD` 固定，前数=虚拟键盘序号（从 1 起，vanilla 不是 VOXKBD 键盘），后数=被映射的**物理键标识**（键盘字母/键名，鼠标/手柄用定义好的 token）。可无限创建、固定可溯、跨四平台与整合包完全一致。**显示名**由用户任意取，且**仅显示名可被材质包覆盖**。 |
| D3 | 按键投递方式（桌面端） | **模拟系统级输入**：桌面端外部进程用 Robot / 键盘钩子注入合成键事件，MC 像收到真实按键一样处理（最版本无关）。Android 端不适用，见 D6。 |
| D4 | 激活模型 | **单一激活**：任意时刻仅一套虚拟键盘生效；上一 / 下一 / 组合键+数字在该套之间切换。锁住的键始终走默认（原版）键盘。 |
| D5 | 跨平台目标 | **四大平台**：Windows / Linux / macOS / Android（FCL、ZL2 等 JVM 启动器）。合成键的"新增 / 注入"逻辑按平台分后端，见 4.0。 |
| D6 | 安卓输入后端 | **进程内 GLFW 注入（mixin 为主、FCL 桥为辅）**：Android 上模组运行于启动器（FCL / ZL2）自带 JVM 内（JVM 与普通 Windows 等价，仅运行时不同），**不另起外部进程**、**不做 Java 路径探测**。实现上以 **Fabric mixin 包住 MC 的 `glfwSetKeyCallback`** 为主，必要时辅以复用 FCL 原生 `GLFW_invoke_Key` 桥（需验证类加载器隔离），见 4.0。 |
| D7 | 安卓聚焦门控 | 以 **MC 前台可见** 为准（FCL 经 `MenuType.GAME` 与 GLFW 窗口焦点属性体现），与桌面 GLFW 窗口聚焦统一，见 3.2。 |
| D8 | 组合键前缀 | **全开放**：`Ctrl` / `Alt` / `Shift` / `Win(Meta)` 任意组合均可作为「组合键+数字」切换的前缀。 |
| D9 | 数字输入（多位） | 「组合键+数字」的数字支持多位：输入一位后模组延迟约 1 秒再切换；该窗口内可续按数字组成多位数（如 `1`+`1`=第 11 套，`1`+`0`=第 10 套）。 |
| D10 | 切换提示默认 | 默认 **动作条（Action Bar）+ 3 秒**。 |
| D11 | 配置格式 | **JSON**（外部进程读取方式据此定）。 |
| D12 | 降级能力（桌面） | **保留完整能力**：Java 探测全失败时降级为进程内 GLFW 钩子，仍实现「新增合成键 + 切换」全套能力，不丢失模组意义。 |
| D13 | ZL2 处理 | **已确认与 FCL 同架构**（基于 Pojav 系 GLFW 注入）：共用 `input_bridge_v3.c` 的 `GLFW_invoke_Key`、`CallbackBridge.sendKeycode` 注入 sink、`InputMap` 应用内映射层（无运行时输入 API）、`VMActivity` 经 `GLFW_FOCUSED` 聚焦门控。安卓后端（D6）对 FCL / ZL2 通用。 |
| D14 | 配置读取（桌面） | **启动传参 + 文件监听热更新**：模组启动时把路径 / 端口传给外部进程，之后 watch 配置文件变化热更新，无需重启进程。 |
| D15 | 绑定来源 | **合成键是"被绑定的按键"（绑定目标），不是功能，绝不进入原版按键配置列表**。原版按键配置界面的语义是「把功能绑定到某个按键」，其条目必须是**功能**（如「打开 UI」「上一个键盘」）；模组在该列表中只注册这三个功能项（§3.3）。功能可以**改绑**到合成键——例如把「打开 UI」的绑定从 `N` 改为某个 `VOXKBD_*` 键码——方式是按固定键码改写功能的绑定键码（整合包默认键位 / options.txt）；原版列表本身不出现任何合成键条目。**绑定抓键流程（v0.5）**：玩家在原版按键配置界面抓键（选中某功能后按键）时，模组把按下的物理键按**当前激活虚拟键盘的合成键码**交给原版记录（此刻锁暂停生效，Esc/修饰键除外），并**自动解锁**对应物理键——否则该合成键永远发不出去，绑定形同虚设；由此形成「切到键盘 N → 原版设置里点功能 → 按物理键 → 记为 VOXKBD_N_X 并解锁 → 生效」的闭环。**仅虚拟键盘的显示名可被材质包覆盖**，内部键名恒定；不开放其它模组程序化注入映射的 API。 |
| D16 | 键码分配 | **固定分配的 GLFW 扩展键码（不注册 KeyBinding）**：每个 `VOXKBD_<虚拟键盘序号>_<物理键标识>` 对应一个由模组固定分配的 GLFW 扩展键码（维护 `键名 ↔ 键码` 分配表），输入后端把该键码投递给 GLFW。合成键**不注册为 MC `KeyMapping`、不出现在原版按键配置列表**——被绑定者放进功能绑定列表毫无意义（D15）。功能改绑合成键 = 把功能的绑定键码改为对应 VOXKBD 键码；跨平台与整合包一致由固定键码表保证。 |
| D17 | 输入来源 | 虚拟键盘的物理输入来源 = **键盘 + 鼠标 + 手柄**（全输入设备），跨平台一致；手柄经 FCL/ZL2 与桌面统一映射为物理键标识。 |
| D18 | 锁的持久化（v0.5 修订，原「强制锁」废止） | **眼见为实**：总控 UI 里红色的键就是锁定的键（永远发原版按键），非红就是未锁（激活虚拟键盘时发 `VOXKBD_*` 合成键）——**抓键绑定时也不许有例外**。锁定/解锁集合（含显式解锁 `unlockedKeys`）**实时持久化**：每一次变更立即写入 JSON，启动时也立即回写；原「未保存按完成强制锁全部」逻辑已删除。默认锁覆盖原版 MC 绑定键（WASD、Shift、F 等），可自由解锁并开启原版跟随（3.4.2）。**VOXKBD 永久跟随**：任一功能绑定到某合成键，其对应物理键永久保持解锁，不受其他配置变更影响。 |
| D19 | 删除行为 | 合成键从未注册进原版按键列表（D16），删除虚拟键盘**无需清理任何 MC 侧注册**，删除即从配置移除、**编号不复用**；删除操作为**选中后点击删除按钮即时生效**（无二次确认弹窗，按已确认的 UI 线框图执行）。 |
| D20 | 默认键盘关系 | vanilla（物理 QWERTY）是独立基底层「**默认键盘**」，永远存在、不可删除；虚拟键盘从 **#1** 起编号（`VOXKBD_1_*`…），**无 `VOXKBD_0`**；切换在默认键盘与各虚拟键盘间循环（**默认键盘可被切到**，v0.5 修订），锁住的键永远发默认键盘的按键。 |

## 2. 核心概念

| 概念 | 英文 | 说明 |
|------|------|------|
| 虚拟键盘 | Virtual Keyboard | 模组在输入层**新增**的一套合成键集合，键名形如 `VOXKBD_<虚拟键盘序号>_<物理键标识>`（如 `VOXKBD_1_W`），与原生物理键盘正交、可无限扩展、跨平台一致。 |
| 默认键盘 | Default Keyboard | 原版（Vanilla）按键层，作为"基准"。被"锁"的按键永远解析到默认键盘。 |
| 锁 | Lock | 把某个物理键固定为「永远发出原版（默认键盘）按键」的机制，使其不被重定向到 `VOXKBD_*` 合成键，不受虚拟键盘切换影响。 |
| 切换 | Switch | 在多个虚拟键盘之间切换当前激活层的行为。 |
| 外部进程 | External Process | 桌面端用 Java 编写的独立进程，承载虚拟键盘输入捕获与转发，与模组强通信；Android 端无此外部进程，改由进程内 GLFW 注入（见 4.0）。 |
| 总控 UI | Master UI | 模组主界面，以"完整键盘"为中心，提供撤回 / 保存 / 完成操作。 |
| 配置界面 | Config UI | 从总控 UI 进入的设置界面，集中所有高级配置。 |

## 3. 功能规格

### 3.1 启动与 Java 探测（Startup & Java Detection）

模组启动虚拟键盘外部进程时，按以下**两级方案**探测 Java 运行环境，并缓存结果：

1. **方案一（PATH 直查）**：在系统 `PATH` 中查找 `java`（Windows 下 `java.exe`）。若找到且可运行，直接使用。
2. **方案二（解析 MC 当前 Java 路径）**：若方案一失败，读取**当前正在运行 MC 的 JVM 所使用的 Java 绝对路径**（例如通过 `java.home` 系统属性或进程命令行解析），使用该 Java 启动外部进程。
3. **缓存（Cache）**：探测成功后，将 Java 绝对路径写入本地缓存配置，下次启动优先使用缓存路径。
4. **降级（Fallback）**：若**所有探测手段均失败**，模组**降级为 GLFW 内置模式**——即不启动外部进程，改用进程内 GLFW 钩子承载（能力可能受限），并**保证模组不崩溃、游戏可正常进入**。

> 设计要点：探查顺序必须是「缓存 → PATH → MC 当前 Java → 降级」，避免每次启动重复探查。
>
> **Android 分支**：在 Android（FCL / ZL2）上，模组直接运行于启动器自带的 JVM 内，**不存在独立的 Java 可执行文件**，故本探测流程不适用，也**无需降级**（启动器本身即 JVM）。Android 采用 4.0 描述的进程内 GLFW 注入后端，无外部进程、无 Java 路径缓存。

### 3.2 窗口聚焦检测（Window Focus Gating）

虚拟键盘**仅在玩家选中（聚焦）当前正在运行的 MC 窗口时**才生效（决策 D7）。统一实现为监听 **GLFW 窗口焦点**：
- 桌面端：模组侧用 `glfwSetWindowFocusCallback` 获取焦点事件，并通过 `focus` 消息同步给外部进程；外部进程在窗口未聚焦时暂停捕获 / 转发。
- Android 端：FCL 已在 `JVMActivity` 生命周期中设置 GLFW 窗口焦点 / 可见属性（`GLFW_FOCUSED`、`GLFW_VISIBLE`），且仅在 `MenuType.GAME` 时把输入送往 MC；模组读取 GLFW 焦点即可判定 MC 是否前台可见，**无需额外检测**。

### 3.3 虚拟键盘切换（Switching）

> **模型（已确认 D2 / D4 / D20）**：虚拟键盘为**新增系统级合成键**，**单一激活**。模组在输入层新增键，键名 `VOXKBD_<虚拟键盘序号>_<物理键标识>`；未锁的物理键被重定向为当前激活虚拟键盘的合成键 `VOXKBD_<当前虚拟键盘>_<物理键>`，锁住的键永远发出原版（默认键盘）按键。切换在「默认键盘 + 各套虚拟键盘」之间发生（**默认键盘可被切到**，v0.5 修订），单一激活，不存在多套叠加。

| 操作 | 触发方式 | 可配置位置 |
|------|----------|------------|
| 上一键盘（Previous） | 快捷键（默认待定） | 原版 `选项 / 按键控制` |
| 下一键盘（Next） | 快捷键（默认待定） | 原版 `选项 / 按键控制` |
| 直接切换至第 N 个键盘 | **组合键 + 数字**（如 `Ctrl+1`、`Alt+3`、`Ctrl+Alt+5`） | **仅模组自身配置界面** |
| 打开配置 UI | 快捷键（默认待定） | 原版 `选项 / 按键控制` |

> **自动锁定保护**：上表四行所涉按键（上一/下一/打开配置 UI、组合键前缀）均为模组注册的原版 `KeyBinding`，**自动纳入默认锁（见 [3.4.1](#341-默认锁-default-lock)）**，在任何虚拟键盘下始终触发原版绑定，**绝不会被重定向为 `VOXKBD_*` 合成键**，从而防止卡死。

规则：

- "上一 / 下一 / 打开配置 UI" 三类快捷键**可在原版选项设置中修改**（复用原版按键控制界面）。
- "组合键 + 数字"切换**必须在模组自己的配置界面修改**；其中**末尾数字（可多位）固定代表目标键盘序号，不可改**，仅允许修改数字前的组合键前缀——前缀为**全开放**（Ctrl / Alt / Shift / Win 任意组合，D8）。数字支持多位输入：输入一位后约 1 秒内可续按组成多位数（D9，如 `1`+`1`=第 11 套，`1`+`0`=第 10 套）。
- 切换后可触发提示（见 [3.7.1](#371-切换提示-notification)，默认动作条 + 3 秒，D10）。

### 3.4 按键锁（Lock）

锁分为三个层面，互相叠加：

#### 3.4.1 默认锁（Default Lock）

- 锁的语义：**无论当前切到哪个虚拟键盘，被锁的按键永远解析到默认键盘（原版）的绑定**。
- 默认行为：在未开启任何额外配置时，**所有原版（Vanilla）按键自动进入锁状态**。
- **模组自身注册的全部 KeyBinding（含：打开总控 UI、上一/下一虚拟键盘、组合键+数字的前缀组合键）均属于“原版按键”范畴，因此自动纳入默认锁保护**；无论切到哪套虚拟键盘，这些键始终触发原版绑定动作，**绝不会被重定向为 `VOXKBD_*` 合成键**，从而防止“按键被抢、无法打开 UI / 无法切回原版”导致的卡死。
- 作用：保证原版操作在任何虚拟键盘下都不受影响。

#### 3.4.2 原版按键锁跟随（Vanilla Key Lock Following）

- 这是一个**可开关的配置项**。
- 开启后，模组**动态跟随原版按键绑定变化**：原版把某个按键绑定到某功能时，模组同时把该按键锁掉，防止该原版功能因虚拟键盘而被"抢键"、导致玩家无法正常使用原版按键。
- 锁的来源是**纯原版**的全量按键集合，**忽略其它模组的按键**（只管好原版）。
- 约束：当此配置开启时，**无法解锁原版当前已绑定的按键**；若玩家尝试解锁，UI 给出提示："请先关闭『原版按键锁跟随』配置，才能解锁该按键"。

#### 3.4.3 UI 中的按键锁（Per-key Lock in Master UI）

- 总控 UI 中心是一张由**所有按键**组成的完整键盘。
- 每个按键可单独锁定 / 解锁：
  - **左键点击** → 锁住该键（背景显示为**红色**）。
  - **右键点击** → 解锁该键。
- 被锁的按键/键盘以**红色背景**直观标识。
- 锁状态为**运行时动态检测**（读取实际按键注册信息），**不硬编码**任何按键列表。

#### 3.4.4 未完成保存的强制锁（Safety Lock on Unsaved Exit）

- 当玩家在**未保存**的情况下点击"完成（Finish）"：
  1. 默认**不保存**任何更改；
  2. **所有当前未锁的物理键强制进入锁状态**（即所有会被 VoxKbd 重定向为 `VOXKBD_*` 的键），回退为原版按键（不再被重定向）；动态检测，非硬编码；
  3. 锁状态以红色背景呈现。
- 默认锁覆盖**原版 MC 绑定键**（WASD、Shift、F 等），可通过配置自由增删，并可选开启「原版按键锁跟随」（见 [3.4.2](#342-原版按键锁跟随-vanilla-key-lock-following)）。
- 目的：防止玩家误退出导致虚拟键盘"抢键"、影响原版与已有绑定。

### 3.5 外部进程通信（External Process & Strong Communication）

- （桌面端）模组（运行于 MC 进程内）与 Java 外部进程之间为**强通信（Strong Communication）**关系，要求双向、低延迟、带心跳。Android 端无外部进程，见 4.0。
- **进程互监（Mutual Supervision）**：
  - 若 **MC 进程或模组崩溃 / 退出** → 外部进程**立即关闭**。
  - 若 **外部进程异常退出** → 模组**尝试重启**外部进程（自愈）。
- 建议通信方式见 [4.3](#43-通信协议-protocol)。

### 3.6 总控 UI（Master UI）

总控 UI 是模组的"总控中心"，**所有 UI 与文案禁止硬编码**（见 [3.8](#38-本地化与禁止硬编码-i18n)）。

布局与交互：

- **中心**：由**所有按键**组成的完整键盘（虚拟键盘的可视化总览）。
- **右下角**：三个按钮 —— **撤回（Undo）**、**保存（Save）**、**完成（Finish）**。
- **状态逻辑**：
  - 未发生未保存更改时：撤回、保存为**灰色（禁用）**。
  - 发生更改后：撤回、保存变为**亮（可用）**。
  - 点击**保存**：写入配置；若无新的未保存更改，撤回 / 保存回到灰色。
  - 点击**撤回**：撤销自上次保存以来的更改；保存恢复为灰色（撤回亦随之变灰）。
  - 点击**完成且未保存**：按 [3.4.4](#344-未完成保存的强制锁-safety-lock-on-unsaved-exit) 执行强制锁与放弃保存。

## 4. 技术设计

> 本章为实现建议，具体选型（通信库、配置格式、加载器）以评审结论为准。

### 4.0 跨平台支持与输入后端（Platform & Input Backend）

Vox Kbd 需在 Windows / Linux / macOS / Android 四大平台运行（D5）。关键结论来自对 FCL 1.3.2.6 源码的只读探查：

- FCL / ZL2 是 Android 上的 JVM 启动器，MC 运行于其内置 JVM；它们把触摸 / 手柄输入**直接喂进 GLFW 输入队列**（`FCLauncher/.../jni/input_bridge_v3.c` 的 `GLFW_invoke_Key`），对 MC 而言与真实键盘无异。
- **FCL 未暴露任何运行时输入 API**（无 BroadcastReceiver / ContentProvider / AIDL / 导出 Service）；其按键映射层是启动器自身 App 类加载器里的 Android UI，Fabric 模组在 MC 的独立类加载器内**无法直接调用**。
- **ZL2（tag 2.4.11）经源码核查，与 FCL 同架构**：同样使用 `input_bridge_v3.c` 的 `GLFW_invoke_Key`、同样的 `CallbackBridge.sendKeycode` 注入 sink、独立的 `InputMap` 应用内映射层（类比 FCL 控制器，无运行时输入 API）、`VMActivity` 经 `GLFW_FOCUSED` / `GLFW_VISIBLE` 做聚焦门控。故 D6 的安卓后端对 FCL 与 ZL2 通用。

因此架构抽象为「**重映射引擎（平台无关）＋ 输入后端（平台相关）**」：

| 平台 | 输入后端 | 说明 |
|------|----------|------|
| Windows / Linux / macOS | **外部 Java 进程 + 系统级注入** | 捕获物理键盘 → 按激活虚拟键盘重映射 → Robot / 键盘钩子注入 OS → MC 的 GLFW 收到（D3）。 |
| Android（FCL / ZL2） | **进程内 GLFW 注入** | 模组在启动器 JVM 内运行（FCL / ZL2 的 JVM 与普通 Windows 等价，仅运行时不同），生成 `VOXKBD_*` 合成键事件并写入 GLFW 输入层（与 FCL 送触摸键同 sink，D6）。不另起进程、无 Java 探测。 |

> 统一点：所有平台最终都落在 **GLFW 输入层**，故「聚焦门控」统一为 GLFW 窗口焦点（见 3.2）；「强通信 / 进程互监」仅桌面端外部进程需要（见 3.5、4.5）。又因 FCL / ZL2 的 JVM 与普通 Windows 等价（仅运行时不同），桌面端的「新增合成键」思路在安卓同构，差异仅在注入落点：安卓走 FCL 的 GLFW 桥，而非 OS 级 Robot。
>
> **键码分配（D16）**：每个 `VOXKBD-<kb>-<btn>` 对应一个**固定的 GLFW 扩展键码**（由模组维护 `键名 ↔ 键码` 分配表）。合成键**不注册**为 MC KeyBinding、不出现在原版按键配置列表（D15/D16）；输入后端在玩家操作时把该键码投递给 GLFW，功能要落到某个合成键时按固定键码改绑（整合包 / options.txt）。因键码由模组固定分配，跨平台与整合包一致。

### 4.1 总体架构（Architecture）

```
┌─────────────────────────────┐        强通信 (心跳 + 命令/事件)        ┌─────────────────────────────┐
│  MC 进程内（模组侧）         │  ─────────────────────────────────▶  │  外部 Java 进程              │
│  - 加载器插件 (Forge/...)    │  ◀─────────────────────────────────  │  - 虚拟键盘输入捕获          │
│  - 窗口聚焦监听 (GLFW)       │                                       │  - 按键转发 / 映射           │
│  - 锁状态管理                │                                       │  - 接收焦点/激活层指令        │
│  - 总控/配置 UI             │                                       │  - 心跳维持                  │
│  - Java 探测与缓存           │                                       │                             │
└─────────────────────────────┘                                       └─────────────────────────────┘
        │                                                                  │
        └──────── 配置持久化（共享给外部进程读取） ────────────────────────┘
```
> 注：上图为**桌面端**架构。Android 端无外部进程（见 4.0），重映射在模组进程内完成并直接注入 GLFW。

### 4.2 外部进程（Java）设计

- 使用纯 Java 编写，避免依赖特定 MC 版本 API，从而**兼容全版本**。
- 职责：
  - 生成虚拟键盘的合成键输入（将物理输入翻译为 `VOXKBD_<键盘>_<按钮>` 事件，或按需产生新键事件）；
  - 依据模组下发的"当前激活虚拟键盘"与"锁状态"做映射；
  - **以系统级输入（Robot / 键盘钩子）将映射结果注入操作系统，使 MC 像收到真实按键一样处理（D3）**；
  - 维持心跳、响应聚焦 / 关闭指令。
- 以 `java -jar voxkbd-daemon.jar` 形式启动，参数含通信端口 / 管道名与 MC 进程标识。
- 说明：因采用 D3，MC 侧**无需改动按键处理逻辑**，模组只负责下发状态（激活层、锁状态、聚焦）与控制外部进程生命周期。
- 注：本小节为**桌面端（Win / Linux / macOS）**后端。Android 端不涉及外部进程与 Java 探测，改为进程内 GLFW 注入（见 4.0 / D6）。

### 4.3 通信协议（Protocol）

建议采用**本地 TCP（localhost）**或**命名管道（Windows Named Pipe）**，消息使用轻量文本协议（如 JSON 行）：

- **心跳（Heartbeat）**：双向周期性 ping/pong，超时即判定对端失效。
- **模组 → 外部进程**：
  - `focus`：窗口聚焦状态变化（true/false）。
  - `active_keyboard`：当前激活的虚拟键盘序号。
  - `lock_state`：按键锁状态快照（动态生成）。
  - `shutdown`：MC/模组退出，要求外部进程立即关闭。
- **外部进程 → 模组**：
  - `key_event`：经虚拟键盘映射后的按键事件。
  - `heartbeat` / `alive`。
  - `daemon_exit`：外部进程自身即将退出（供模组触发重启逻辑）。

### 4.4 Java 探测、缓存与降级（Detection, Cache, Fallback）

- 探查顺序：`缓存路径 → PATH 查找 → MC 当前 JVM 路径（java.home/进程命令行） → 降级`。
- 缓存写入本地配置文件（如 `voxkbd.json` 的 `javaPath` 字段）。
- 降级实现：不启动外部进程，回退到**进程内 GLFW 钩子**模式；该模式下至少保证"锁"与基本可用性，**模组绝不崩溃**。

### 4.5 进程监督与自愈（Supervision & Self-heal）

- 模组持有外部子进程句柄，监听其退出；外部进程亦监听 MC 进程/套接字断开。
- MC 退出 → 外部进程收 `shutdown` 或检测到连接断开 → 立即退出。
- 外部进程异常退出 → 模组按 [3.1](#31-启动与-java-探测-startup--java-detection) 的探测逻辑**尝试重启**，并限制重启次数/退避，避免抖动。

### 4.6 窗口聚焦实现（Window Focus）

- 模组侧利用 GLFW 的窗口焦点回调（`glfwSetWindowFocusCallback`）获得聚焦事件。
- 聚焦状态通过 `focus` 消息同步给外部进程；未聚焦时外部进程挂起捕获。

## 5. 实现方案细化（Implementation Detail）

> 本章在 D1–D16 基础上细化落地，仍为方案级（不动代码）。模块、协议、键码分配、配置 schema 均为建议实现，参数可在实现期微调。

### 5.1 模块划分（Module Breakdown）

| 模块 | 形态 | 主要职责 | 平台 |
|------|------|----------|------|
| `voxkbd-core` | 共享库（加载器无关） | `VOXKBD` 前缀与命名规则、键码分配表、配置 schema、协议消息类型与常量 | 全平台 |
| `voxkbd-mod` | Fabric 模组 | 锁管理、切换管理、UI（总控/配置）、i18n、配置持久化；桌面端 Java 探测/缓存/启动监督 daemon；全平台仅注册三个切换功能 `KeyBinding`（合成键不注册，D16）、聚焦监听 | 全平台 |
| `voxkbd-daemon` | 独立 Java 进程（桌面） | 捕获物理输入 → 按激活键盘+锁状态翻译为 `VOXKBD_*` 合成键 → OS 级注入（Robot/键盘钩子）；心跳、配置热更新（watch） | 仅桌面 |
| `voxkbd-mixin` | Fabric mixin（安卓） | 包住 MC `glfwSetKeyCallback`，进程内生成 `VOXKBD_*` 合成键事件 | 仅安卓 |
| `voxkbd-fclbridge` | 安卓辅助（可选） | 复用 FCL/ZL2 原生 `GLFW_invoke_Key` 桥（待验证类加载器隔离） | 仅安卓 |

> 桌面端输入链路：`物理键 → daemon(翻译+注入) → OS → MC(GLFW)`；安卓端：`物理/触摸键 → mixin(翻译+注入 GLFW) → MC`。两者都落在 GLFW 层（D16）。

### 5.2 通信协议细化（桌面 daemon ↔ mod，D3/D14/D16）

- **传输**：localhost TCP（默认）或 Windows 命名管道；**JSON 行协议**（每行一个 JSON + `\n`）。
- **端点**：模组启动时生成端口/管道名，随启动参数传给 daemon（D14）；daemon 连回模组。
- **超时**：心跳 3s 未收到对端 → 判定失效（触发关闭/重启，见 3.5/4.5）。

消息示例：

```jsonc
// 握手
mod  → daemon : {"t":"hello","mcPid":12345,"ver":"0.1"}
daemon → mod  : {"t":"ready"}

// 心跳（双向）
mod  → daemon : {"t":"ping","ts":1700000000000}
daemon → mod  : {"t":"pong","ts":1700000000000}

// 状态下发：激活键盘 + 锁集合 + 聚焦（mod → daemon）
mod  → daemon : {"t":"state","activeKeyboard":3,"focus":true,
                 "lock":[["A","SPACE"],["W"]]}   // 被锁的物理键（vanilla keycode/名），daemon 据此绕过重映射

// 配置热更新触发（可选，daemon 也可自行 watch）
mod  → daemon : {"t":"reload"}

// MC/模组退出
mod  → daemon : {"t":"shutdown"}
// daemon 自身将死
daemon → mod  : {"t":"daemon_exit","reason":"oom"}
```

> 注：daemon **不回传 key_event**——它直接 OS 级注入，MC 像收到真实按键一样处理（D3/D16）。mod 侧仅下发状态、收心跳与退出信号。

### 5.3 VOXKBD 键码分配表（Keycode Allocation，D16/D17）

- **区分两层**：内部名 `VOXKBD_<虚拟键盘序号>_<物理键标识>`（如 `VOXKBD_1_W`）是*标识符*；GLFW *键码*是数值，由模组**固定分配**，保证跨平台/整合包一致。
- **固定物理键序列表（跨平台一致）**：所有可被映射的物理输入编入一张固定序列表——键盘键（A–Z、0–9、功能键、Shift/Ctrl/Alt…）→ 鼠标键（ML/MR/MM…）→ 手柄键（GP_A/GP_B…）。每个物理键在表中有固定序号 `idx`。
- **分配公式**：
  `keycode = VOXKBD_BASE + kb * VOXKBD_STRIDE + idx(物理键)`
  - `VOXKBD_BASE = 400`（GLFW 标准键码上限 ~348 之上，留缓冲）
  - `VOXKBD_STRIDE = 256`（不小于固定物理键序列表长度，使每套虚拟键盘可映射全部物理键；`kb` 可很大）
- **示例**（设 `idx(W)`、`idx(A)`、`idx(ML)` 由固定序列表决定）：
  - `VOXKBD_1_W` → 400 + 1×256 + idx(W)
  - `VOXKBD_2_A` → 400 + 2×256 + idx(A)
  - `VOXKBD_1_ML`（鼠标左键）→ 400 + 1×256 + idx(ML)
- **MC 侧**：**不注册** `KeyMapping`，原版按键配置列表中**没有任何合成键条目**。原版列表的条目是「功能」（需要绑定按键的功能项，如「攻击」「打开 UI」），合成键是「被绑定的按键」（绑定目标）——把被绑定者放进功能列表毫无意义（D15）。功能要落到某个合成键时，直接把该功能的绑定键码改为对应 VOXKBD 键码（整合包默认键位 / options.txt 按固定键码引用，D16）。
- **边界**：keycode 取 int；按 STRIDE 256、`kb` 很大仍 < 65536；实际上限以 LWJGL/MC 实现为准，参数实现期微调（不阻塞）。

### 5.4 JSON 配置 schema（具体化，D11/D14/D15）

```json
{
  "version": 1,
  "javaPath": "C:/.../java.exe",        // 桌面缓存；安卓无此字段
  "fallbackEnabled": true,              // 探测失败降级 GLFW（D12 保留完整能力）
  "focusGating": true,                  // 仅聚焦 MC 窗口时启用（D7）
  "vanillaLockFollow": false,           // 原版按键锁跟随（3.4.2）
  "switch": {
    "previousKey": "unknown",           // 上一键（原版按键控制可改）
    "nextKey": "unknown",               // 下一键
    "openConfigKey": "unknown",         // 打开配置 UI
    "comboPrefix": "CTRL_ALT",          // 组合键+数字 前缀（全开放，存组合位掩码）
    "comboDigitDebounceMs": 1000,       // 多位数字输入防抖（D9）
    "notification": {
      "type": ["ACTION_BAR"],           // 默认动作条（D10）
      "durationSec": 3,
      "persistOnHome": false
    }
  },
  "keyboards": [                        // 虚拟键盘列表（显示名任意，仅显示名可材质包覆盖）
    { "id": 0, "displayName": "默认", "nameKey": "voxkbd.kb.0", "resourcePackOverride": true }
  ],
  "keycode": { "base": 400, "stride": 64 },   // 键码分配参数（D16）

```

### 5.5 启动 / 探测 / 降级时序

**桌面（Win/Linux/macOS）**
1. 模组初始化 → 读缓存 `javaPath`（无则 PATH → MC 当前 JVM → 降级）。
2. 启动 `voxkbd-daemon.jar`（传端口/路径）→ 握手 `hello/ready` → 互启心跳。
3. 模组注册三个切换功能 `KeyBinding`（合成键不注册，D16）→ 加载配置 → 下发 `state`。
4. 若 daemon 退出 → 模组按 3.1/4.5 重启；若 MC 退出 → 发 `shutdown`。

**安卓（FCL/ZL2）**
1. 模组在启动器 JVM 内初始化（无 Java 探测、无 daemon）。
2. 注册 mixin（包住 `glfwSetKeyCallback`）；可选注册 FCL 桥调用（D6）。
3. 注册三个切换功能 `KeyBinding`、加载配置、读取 GLFW 聚焦（D7）。
4. 无进程监督（同一 JVM）。

### 5.6 一次按键的运行时流程（锁 + 切换，D2/D4/D16）

```
物理键按下
  └─ 桌面: daemon 捕获；安卓: mixin 拦截 glfwSetKeyCallback
       ├─ 该键在 lock 集合? ── 是 ─→ 注入原版键码（永远默认键盘）
       └─ 否 ─→ 翻译为 VOXKBD_<当前虚拟键盘>_<物理键标识> 键码
                  └─ 注入该合成键码（GLFW）
                       └─ MC 收到 → 绑定到该键码的功能触发
                          （功能改绑到合成键后即由合成键驱动，D15/D16；
                           未改绑的合成键码在 MC 内无对应功能，等于空闲按键）
```

切换键盘：模组更新 `activeKeyboard` → 桌面下发 `state` 给 daemon / 安卓 mixin 读共享状态 → 后续未锁键即映射到新键盘的合成键。

### 5.7 UI 与 i18n 模块（见 3.6 / 3.7 / 3.8）

- 总控 UI：中心完整键盘视图 + 撤回/保存/完成状态机（3.6）；所有字符串走 i18n，禁硬编码。
- 配置 UI：切换提示、虚拟键盘管理（显示名可材质包覆盖）、原版锁跟随等（3.7）。
- i18n 键示例：`voxkbd.ui.undo`、`voxkbd.ui.save`、`voxkbd.ui.finish`、`voxkbd.kb.<id>`（显示名）、`key.voxkbd.<kb>.<btn>`（键标签）。

## 7. 术语表

| 术语 | 英文 | 含义 |
|------|------|------|
| 虚拟键盘 | Virtual Keyboard | 与物理键盘正交的按键映射层 |
| 默认键盘 | Default Keyboard | 原版的按键层，作为锁定基准 |
| 锁 | Lock | 固定按键到默认键盘的机制 |
| 原版按键锁跟随 | Vanilla Key Lock Following | 动态跟随原版绑定并自动锁对应按键 |
| 切换 | Switch | 在虚拟键盘间切换激活层 |
| 外部进程 | External Process | 承载虚拟键盘的 Java 独立进程 |
| 强通信 | Strong Communication | 带心跳的双向可靠通信 |
| 降级 | Fallback | 探测失败时回退到 GLFW 内置模式 |
| 总控 UI | Master UI | 模组主界面（中心键盘 + 撤回/保存/完成） |
| 资源包干预 | Resource Pack Override | 名称等可被材质包覆盖 |
